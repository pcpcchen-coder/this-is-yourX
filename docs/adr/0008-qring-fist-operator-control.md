# ADR-0008: 用智慧戒指握拳控制右手（操作者的控制方法之一），並開 `control_methods/` 放這類方法

- Status: proposed（2026-10-11 依 George 的要求實作並安裝；是否接受由 George 決定）
- Date: 2026-10-11
- Owners: George / project maintainers

## Context

George 有一顆 QRing R08 智慧戒指（資料在 [pcpcchen-coder/qringr08plus](https://github.com/pcpcchen-coder/qringr08plus)），
要用它的三軸數據控制右手：他握拳時，手跟著握拳。要一個裝在他那台 Mac 上的 App，有校正介面、啟動開關與戒指資訊。
手仍然接在 Raspberry Pi 上（[ADR-0007](0007-hand-operator-web-panel.md)）。他說這是控制手的方法之一，之後還會用雙目相機
（[ADR-0005](0005-stereo-camera-ar0144.md)）做另一種。

已知的條件：

- 戒指只有三軸加速度計（含重力），沒有確認到陀螺儀；已在這顆戒指上驗證過的讀法是藍牙快照輪詢，實測約 1–10 Hz。
  它的藍牙協定只在 macOS（bleak／CoreBluetooth）上驗證過。
- 面板的 HTTP 介面已經提供人工操作需要的一切：啟用扭力（先把目標設成目前位置）、設四指目標、停止、心跳看門狗、閒置逾時、
  落後／電壓／溫度／掉線／到位檢查與 fault 鎖定。2026-10-08 在實機上用過（ADR-0007）。
- `hand_api`（[ADR-0006](0006-hand-skill-api-mcp.md)）是給 AI 用的，刻意不接受角度，v1 明寫不做連續遙操作，實機動作也還沒開放。
- 限制沿用既有規則：生成式模型不得下 raw motor 命令；前置條件為 false 或 unknown 一律拒絕；停止與安全狀態不得依賴 LLM 或網路；
  沒有獨立的 E-stop，只有延長線開關（[AGENTS.md](../../AGENTS.md)、[07](../07_SAFETY_SECURITY_PRIVACY.md)）。

## Decision

1. 在 `right_hand/` 底下開 `control_methods/`，放「操作者用某種輸入裝置控制右手」的方法，一種方法一個資料夾。
   原有的網頁操作面板與 `hand_api` 留在原位。
2. 第一種方法 `control_methods/qring_fist/`：一個 macOS App（QRing Hand），做法是：
   - 戒指用藍牙接在 Mac 上。校正記下「張開」「握拳」兩個重力方向；之後把目前的方向投影到兩者之間的弧線上，得到握拳程度 0–1，
     再線性內插成四指的彎曲與側擺。全部是固定的幾何換算，沒有模型。
   - 對手的所有動作都經由面板既有的 HTTP 介面，身分是「一個控制的頁面」。**面板與 `hand_api` 的程式都不改**；
     接著手的主機上不需要裝任何新東西。
   - App 這一側再加的條件：啟動要人按兩次；啟動前要有 1 秒內而且有效的握拳讀值、面板沒有 fault、匯流排 attached、
     8 顆都回應、沒有別的頁面在控制；讀值無效（大小不在 0.8–1.2 g、離開校正弧線超過容許角度、超出兩端太多）時不送新目標；
     戒指斷線、App 結束就送關扭力；面板關了扭力就跟著停，不自己再啟動；「長按戒指啟動」預設關閉。
3. 定位和面板相同：給人用的工作台工具，不是 skill，也不是 AI 的控制路徑。

細節在 [`right_hand/control_methods/qring_fist/README.md`](../../right_hand/control_methods/qring_fist/README.md)；
這類方法共同的界線寫在 [`right_hand/control_methods/README.md`](../../right_hand/control_methods/README.md)。

明確不在這次決策內：

- **不改變 ADR-0006 與 ADR-0007。** AI 仍然只能經 `handd` 提議已校正的手勢並逐次核准。這個 App 的本機服務和面板的 HTTP 介面
  一樣會讓手動起來，不得接到任何模型或 agent 上。
- 不把 App 的「停止」當成 E-stop。
- 不做抓握、接觸物體、個別手指、手勢辨識、左手。
- 不決定雙目相機那一種方法怎麼做；只先把放的位置和共同的界線定下來。
- 不替這類方法定義共用的程式介面（目前只有一種方法，沒有第二個例子可以對照）。

## Alternatives considered

- **在接著手的主機（RPi）上直接連戒指**，和面板跑在同一台：少一段網路，Mac 不必開著。但戒指的協定只在 macOS 上驗證過，
  Linux／BlueZ 上沒有試過；George 要的是 Mac 上的 App；而且會在面板旁邊多一支碰同一隻手的程式。不採用，列為 Revisit 條件。
- **替面板加一條串流介面（WebSocket）**：延遲可能小一點，但要改已經在實機上用過的面板，並在接著手的主機上重新部署。
  既有的 `/api/fingers` 本來就支援拖滑桿時連續改目標（新目標取消進行中的那一段），先用它。不採用。
- **經過 `handd` 的 gateway**：gateway 的契約是不接受角度、每個動作逐次核准、不做連續遙操作。要讓跟隨可用，就得在 AI 用的
  gateway 裡替操作者開一條接受連續目標的旁路，和 ADR-0007 拒絕的理由相同。不採用。
- **做進 QRing Studio**（戒指 repo 既有的 App）：少一個 App，但會把控制機器手的程式和戒指的開發工具綁在一起，
  而且重新簽署會讓 QRing Studio 既有的 macOS 授權失效。分成兩個 App；用「連線前問本機的 QRing Studio 是否連著戒指」避免兩邊同時連。
- **App 自己開序列埠控制伺服機**：手不在 Mac 上，而且會繞過面板的檢查與匯流排鎖。不採用。
- **只做兩段（張開／握拳）**：對每秒幾筆、有雜訊的讀值比較穩，但少了「握多少跟多少」。兩種都做，預設連續，設定裡可以換。

## Consequences

- 面板多了一種客戶端：不是瀏覽器頁面，而是另一台機器上的程式，以每 0.12 秒最多一次的頻率連續改目標。面板的稽核紀錄裡，
  它的呼叫者是 `operator.web:ringhand…`。ADR-0007 記下的風險（區域網路上沒有登入、接受任意角度）不變，這個 App 沒有讓它更寬，
  也沒有讓它更窄。
- **手的動作現在由穿戴式感測器的讀值連續驅動。** 風險與緩解：
  - 單顆加速度計分不出「握拳」和「轉手腕／前臂」。離開校正弧線太遠時不送新目標，但沿著弧線方向的手腕動作會被當成握拳。
    緩解：啟動要人按兩次、操作者看著手、實體開關；手的活動範圍內不放東西。
  - 讀值無效或戒指資料中斷時手停在上一個位置、扭力還開著，要等面板的閒置逾時（預設 60 秒）才放鬆。這是沿用面板的行為，沒有另外加短逾時。
  - 沒有電流或力回授（ADR-0007 的限制）；手指頂到東西時，要落後超過上限才會停。不要用它抓握。
  - 戒指的觸控可能誤觸。長按啟動預設關；長按停止預設開（誤觸的結果是停下來）。
- 停止這條路變長了：Mac 上的 App → 區域網路 → 面板 → 伺服機。Mac 當機或斷網時，靠面板的 3 秒心跳看門狗；面板或主機當掉時只有實體開關。
- App 連著面板時，面板佔著匯流排，`finger_cal.sh`、`handd --adapter scs` 會回報被占用（和頁面開著時相同）。
- 多一組相依與平台：macOS、Apple Python 3.9、`bleak`、`pyobjc`、`aiohttp`、`swiftc`、ad-hoc 簽章；和 `right_hand/requirements.txt` 分開。
  戒指的協定知識在另一個 repo，這裡的 `ring.py` 是從那邊已驗證的部分抄過來的，兩邊要各自維護。
- 新增 47 項測試（模擬戒指＋模擬面板），不在 `pytest right_hand/tests -q` 裡；原有測試不變。
- 目前的手感受限於戒指的更新率（實機上看到約 4 Hz）。

## Validation

- 已做（2026-10-11）：47 項測試在開發環境與 George 的 Mac（Apple Python 3.9）上通過，全部用模擬戒指與照面板 HTTP 介面做的假面板。
  啟動前條件不成立的案例都檢查沒有送出 `enable`；另外涵蓋讀值無效時不送目標、戒指斷線關扭力、面板放鬆／鎖定／連不到時停止且不自行重啟、
  結束時關扭力、長按啟動預設關、本機服務的來源檢查。
- 已做（開發環境）：接上真的 `hand_panel` 程式（模擬 adapter）跑整條路徑——握拳、張開、來回、閒置逾時後 App 跟著停、
  結束 App 後扭力關、心跳停掉後面板約 3 秒關扭力。模擬 adapter 的目標一寫入就到位，所以這不能說明實機上的落後行為。
- 已做（bring-up 觀察，沒有 experiment ID；依據是面板的稽核紀錄最近 100 筆）：2026-10-11 George 用真的戒指與實機操作了兩段
  （10:46–10:47、13:31–13:32，中速、連續模式、內建握拳）。96 段移動全部到位並停下，沒有 fault；到位後目標與實際的差平均 1.9°、
  最大 3.8°；握到 85°、張開到 −30° 都走過。寫程式的這一方（AI）沒有對實機下過任何動作，只讀了面板的狀態與紀錄。
- **還沒做**：實機上的中止路徑（閒置逾時、fault 鎖定、心跳看門狗、戒指斷線、App 被強制結束、Mac 斷網）；慢速與快速；
  長時間使用；端到端延遲；搬到 `control_methods/qring_fist/` 之後的建置腳本在 Mac 上重跑。做完並有 experiment ID、硬體版本與
  [07 §10](../07_SAFETY_SECURITY_PRIVACY.md) 的檢查表之前，不能寫成 real-hardware validation。

## Revisit when

- 做第二種控制方法（雙目相機）時：檢討 `control_methods/README.md` 的共同界線夠不夠，要不要抽出共用的「握拳程度 → 面板」那一段。
- 裝了固定的實體開關或 E-stop。
- 要讓手在 Mac 沒開著的時候也能用戒指控制，或要在 Linux 上驗證戒指的協定（那時重新考慮把戒指接在接著手的主機上）。
- 更新率或延遲成為主要限制，需要面板提供串流介面時。
- 面板的存取控制改變（開回 `--require-token`、換網段）時：App 目前不帶存取碼。
- 想讓 AI 觸發或調整這種跟隨時：那是 ADR-0006 的範圍，不能經由這個 App 的本機服務。
